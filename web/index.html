Check a Safe
For teams that pay from a Safe

Check every payment before the last signature.

Paste a Safe. Rein checks each transaction waiting for signatures against what that Safe has actually paid before, and tells signers which ones pay an address dressed up as one they use, a stranger, or far more than usual. Free and read-only: no keys, no setup, nothing signed.

No Safe handy? Try a made-up one with a poisoned payment queued. Signing every week? Add Rein to Safe{Wallet} as a custom app and it checks the Safe you're in, next to the queue.

How it works

Checked against who your Safe has really paid, and how much.

Address poisoning sends a Safe tiny fake transfers from addresses that start and end like its real payees, hoping someone copies one from the history. The next signer sees a familiar-looking address and signs. Safe{Wallet} compares lookalikes only against each signer's own address book, and its "New recipient" label is moving to Safe Pro, its paid plan. Rein compares every queued payee with the payees this Safe has really paid, character for character, and the amount with the most it has paid them, free.

  1. Paste

    Any Safe on Base or Ethereum. Rein reads its queue from Safe's public service and its history from the chain, and marks each transaction "Looks normal", "Check first" or "Don't sign yet", with the reason.

    rein-nine.vercel.app/safe

  2. Next to the queue

    In Safe{Wallet}, open Apps, then My custom apps, and add Rein. Every signer gets the check on the Safe they're signing for. It only reads: it never proposes or signs.

    https://rein-nine.vercel.app/safe/

  3. Told first

    A copyable GitHub Action checks the queue every 10 minutes and posts each risky transaction once to Slack, Discord or Telegram, before the last signature. No server.

    npx rein-wallet safe 0xYourSafe \
  --webhook "$SLACK_WEBHOOK_URL"

What it doesn't claim: a flag means confirm the address another way, not that it's an attack, and a payee it doesn't flag isn't vouched for. It checks against this Safe's own history, not scam lists.

Before and after

Every wallet engine will enforce a limit. Nobody tells you which limit.

Privy, Turnkey and Coinbase all ship policy engines. They enforce whatever rule you type in. So most agent wallets run with no rule at all, or a guess, because a limit that's too tight breaks the agent at 3am and one that's too loose stops nothing.

how agent wallets run today

You guess the limit, or skip it

  • A blank policy, or one flat cap that has no idea who the money goes to.
  • No way to know whether a tighter rule would have blocked last week's honest payments.
  • Hand-writing JSON in three different policy languages if you use more than one engine.
  • Finding out from users when an injected instruction moves funds.
with Rein

The limit comes from the agent's own history

  • Payees, contracts, functions and hourly ceilings learned from what the wallet already does.
  • One line before signing holds transfers, router swaps and signatures (x402, Permit, Permit2) to them, with a reason the agent can act on.
  • Measured before you ship it: replayed on recent calls it never saw, with the count that would have been blocked.
  • Rein as a second key on Turnkey or Privy: the agent signs alone inside its limits, and anything else needs Rein's co-signature or a person's approval in Slack. The requests are printed first, so nothing surprises you.
  • An alert on the first transaction outside it, in Slack or Discord, with no server to run.
May 2026

A token sent to a Grok-linked agent wallet on Bankr unlocked more of what the agent was allowed to do, and the agent was then talked into sending funds out. Limits learned from a wallet's own history don't widen because a token or a message says so. Only the owner can widen them, at a keyboard, and a payment to an address the agent has never paid is blocked until they do.

How it works

Watch first. Then make it a second key.

  1. Shadow

    Give Rein your agent wallets. It learns each one's limits from its history before the last 30 days, then posts to Slack every payment since that a second key would have held. Read-only.

    npx rein-wallet fleet wallets.txt \
  --webhook "$SLACK_WEBHOOK_URL"

  2. Second key

    One command makes Rein a co-signer your wallet engine enforces. Inside its limits the agent signs alone; anything else waits for Rein, which approves what fits the hour and the day.

    npx rein-wallet cosign setup turnkey \
  --organization <org> \
  --agent-user <id> --send

  3. Hold

    What doesn't fit goes to Slack with an Approve link and a Refuse link. An approval lets that one payment through once. New wallets start from the limits their siblings share.

    npx rein-wallet approvals \
  --public-url https://… \
  --webhook "$SLACK_WEBHOOK_URL"

Running one agent of your own? npx rein-wallet guard 0xAgent learns its limits, and require("rein-wallet").check(tx) holds each payment to them before it signs.

Why Rein

Policy engines enforce the rule. Rein writes it.

Rein does for agent wallets what IAM Access Analyzer does for cloud permissions. It reads what the agent actually does and proposes the tightest policy that still lets it work. It doesn't replace your wallet engine. It fills the blank policy you already have there.

Straight answers

What Rein does, and what it doesn't.

Does Rein need our keys or custody of funds?

No. The scan reads public chain data. apply calls your wallet engine's API with credentials that stay on your machine, and prints every request before it sends one. Nothing moves into a Rein contract unless you choose the Rein account.

We already have a Privy, Turnkey or CDP policy. Does the scan see it?

No, and every report says so. A signing policy held off chain is invisible to a scan of the chain. That's why the report says "no on-chain limit" rather than "anyone can take it". The review compares the compiled policy against the one you already have.

What if the compiled policy blocks something the agent needs?

Every policy comes with the count of recent calls it would have refused. You see those calls before you apply it. Anything rare, like a payee seen only once, is held back for a person to approve instead of being allowed quietly.

Where does the check run?

As a second key, in Rein's co-signer, and your wallet engine enforces it: on Turnkey a policy needs both the agent and Rein outside the learned limits, and on Privy the wallet's owner is any two of the agent, Rein and your admin key. A hijacked agent can't skip a signature it doesn't have. Normal payments never touch Rein, so an outage can't stop them. rein.check(tx) runs the same check inside the agent's own process with no server, which is quicker to start with but can be skipped by an agent whose code is taken over.

Has the co-signer run on a live Turnkey or Privy account?

Not yet. It is built against both vendors' published APIs and tested against stand-ins for them. Shadow mode needs neither, so it is the place to start.

What can't it stop?

A payment the policy allows. If an attacker steers the agent to pay a payee it already pays, inside the hourly and daily ceilings, that goes through, and the replay states how much that could be. Rein bounds how much can move and to whom. It doesn't judge the payments the policy permits. A signature it can't read is blocked; a call to an unfamiliar contract is blocked; a call to a contract the agent already uses, that Rein can't read, is held only to the contracts and functions the agent normally calls.

What chains and engines?

Scans read Base, Base Sepolia and Ethereum. Policies export to Privy, Turnkey and Coinbase CDP, and to the Rein smart account. The code is open source under MIT.

Is the Rein account audited?

Not yet. It is verified on Base Sepolia and Whitechain Sepolia, with its test suite in the repository. For money that matters today, use Rein's policies on the engine you already trust. More about the account.
